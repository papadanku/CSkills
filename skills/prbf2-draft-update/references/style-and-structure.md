
# Developer Blog Style & Structure Guidelines

## Audience & Tone

- **Voice**: Approachable, candid, and technically grounded. Written by a developer or contributor (`Hello, everyone!` / `Hey everyone,`) speaking peer-to-peer with the Project Reality community.
- **Honesty**: Acknowledge trade-offs, current limitations, and design goals upfront. If a feature is still experimental or intentionally scoped down, state why.
- **Clarity**: Explain technical concepts (shaders, guidance math, server architecture, asset pipelines) in accessible language, always tying them back to in-game feel and player impact.

## Structural Conventions

1. **Series Naming**: Multi-part blogs use consistent numbering in the title, such as `<Topic> Part 1/3: <Subtitle>` or `<Map/Feature> Development Update #2 - <Subtitle>`.
2. **Problem-First Framing**: Start by describing the legacy BF2 or PR limitation before presenting the new solution.
3. **Media Integration**: Dev blogs rely heavily on short YouTube demonstrations, before/after screenshots, and clean diagrams. Always insert descriptive `[IMAGE: ...]` or `[VIDEO: ...]` placeholders when media is not yet supplied.
4. **Sign-off**: Individual technical posts are typically signed `- <AuthorHandle>`, while team-wide tooling or branding posts may close with `- The Project Reality Team`.
